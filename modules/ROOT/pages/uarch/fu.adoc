Terminology
-----------

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*",
"*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*NOT RECOMMENDED*", "*MAY*",
and "*OPTIONAL*" in this document are to be interpreted as described in
https://rfc-editor.org/info/bcp14[BCP 14]
{blank}[https://doi.org/10.17487/RFC2119[RFC2119]]
{blank}[https://doi.org/10.17487/RFC8174[RFC8174]]
when, and only when, they appear in all capitals, as shown here.

The term "slice" *SHALL* refer to a fixed-width, non-overlapping portion of
a word, `SLICE_WIDTH` bits wide. A word is divided into `NUM_SLICES` slices.
The exact bit range for a slice *SHALL* be interpreted as described in
requirement `REQ-REGFILE-020`.

The "acceptance" of a particular operation *SHALL* refer to the clock cycle
where the handshake is successful, namely when both `valid_i` and `ready_o`
are asserted.

The "completion" of a particular operation *SHALL* refer to the clock cycle,
following the acceptance of a given operation, on which `ready_o` is reasserted.

The term "operation" *SHALL* refer to one full execution of `fu_op_i`,
from acceptance to completion, as defined above.

The term "cycle" is not to be confused with the counter value `cycle_i`.

IP Overview
-----------

A slice-serial functional unit (FU) for a RISC-V core, operating on one slice
of each operand per cycle. The module accepts an operation over a ready/valid
handshake, processes it over multiple cycles as driven by an externally
supplied cycle count, and writes the result back to the register file
by driving that register file's write port control signals.

Design Constraints
------------------

[cols="1,4"]
|===
| Constraint ID | Description

| `CON-FU-010`
| The maximum number of cycles from acceptance to completion of any operation,
for any valid value of `fu_op_i`, *MUST NOT* exceed 8.
|===

Design Requirements
-------------------

[cols="1,4"]
|===
| Requirement ID | Description

| `REQ-FU-010`
| An operation *SHALL* be accepted on any rising edge of `clk_i` where
`valid_i` and `ready_o` are both asserted. The operation code `fu_op_i`
*MUST* be sampled on this edge.

| `REQ-FU-011`
| The cycle count `cycle_i` *MUST* be driven by the requester on the cycle
immediately following an acceptance, and *MUST* increase by exactly 1 on
each subsequent cycle for the duration of the operation.

| `REQ-FU-012`
| The module *SHALL NOT* rely on any internal counter. Sequencing of an
operation *MUST* be derived from `cycle_i`.

| `REQ-FU-013`
| The ready signal `ready_o` *MUST* be deasserted no later than the cycle
after acceptance, and *MUST* remain deasserted for the entire duration
of an operation.

| `REQ-FU-014`
| The ready signal `ready_o` *MUST* be reasserted on the cycle the operation
finishes processing.

| `REQ-FU-015`
| The result slice `result_o` and writeback signals `wslice_o` *MUST* be valid
when `ready_o` is reasserted to signal the conclusion of the operation.

| `REQ-FU-016`
| The module *MUST* be able to accept a new operation immediately after
reasserting `ready_o`.

| `REQ-FU-020`
| The slice selector `rslice_o` *MUST*, on each cycle of an operation
during which a source slice is fetched, select the source slice
required by `fu_op_i` for that cycle.

| `REQ-FU-021`
| The slice selector `wslice_o` *MUST*, on each cycle of an operation
during which a result slice is written back, select the destination
slice corresponding to `result_o` for that cycle.

| `REQ-FU-030`
| For each valid value of the operation code `fu_op_i`, the sequence of result
slices `result_o` produced over an operation *MUST* correspond to the result
as defined for that operation code.
|===

Architecture
------------

The module is a slice-serial functional unit sequenced externally by `cycle_i`
rather than by an internal counter. Upon acceptance, it latches `fu_op_i`.
The operand slices `a_i` and `b_i` are fetched one cycle per slice as `cycle_i`
advances and handled by `rslice_o`. The result slice `result_o` and the
write slice select `wslice_o` correspond to the result of the operation.

=== Cycle Sequencing

Because `cycle_i` is driven by the requester, the module decodes `fu_op_i`
to determine sequencing of the operation.

== Implementation Notes

The following documents implementation decisions, including intentional
deviations from standard practice and known limitations.

* Writebacks assume that the result slice `result_o` is either valid, or will
be overwritten afterwards during the same operation.

* Shift operations will not work properly when the source operand and
destination point to the same register.

The following lists the open items that will be resolved in a future revision:

* To support shift operations with the same source and destination register
(see above), a future revision shall sequence through each slice twice during
a shift: the first for fetching and processing; and the second time for
writeback.

* Support for the Zicond extension operations `CZERO.EQZ` and `CZERO.NEQ`
is planned.
